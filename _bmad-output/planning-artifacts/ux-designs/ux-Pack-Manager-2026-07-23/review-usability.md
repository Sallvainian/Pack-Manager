# Usability Review — Pack-Manager UX Spines

Reviewed as a build contract for the unimplemented 28-story Epic UX-PB. Lens: usability.
Targets: `DESIGN.md` (252 lines), `EXPERIENCE.md` (460 lines), both `status: final`.

## Overall verdict

The prior review's twelve findings are almost entirely closed — eleven resolved outright, and the spines are now materially stronger on plan editability, bulk-selection scope, confirmation-off labelling, and Retry/History lineage. What remains is a different and more serious class of problem: the spines specify the *draft* lifecycle in depth and the *execution* lifecycle thinly. Three defects are build-blockers — the single sidecar has two mutually exclusive required occupants at the same time, the `Verifying` state that the whole verification-gated trust story rests on appears zero times in `DESIGN.md`, and the one control that stops a machine-mutating run has two different labels in one document and no specified home during ordinary execution.

## Findings

- **[critical]** **The single Upgrade Sidecar has two mutually exclusive required occupants at the same time, and the spines assert both.** `EXPERIENCE.md:100` states the scenario explicitly. Quote: "A user may continue / reviewing a draft, but it cannot be confirmed until the active attempt is / terminal." But the sidecar is simultaneously committed to the live attempt — `EXPERIENCE.md:62` "The same sidecar persists at terminal state until `Done`" — while the draft rule at `EXPERIENCE.md:179` is unconditional: "First eligible addition: sidecar opens with focus preserved on the source control." Epic UX-PB.3a repeats the collision rather than resolving it (`_bmad-output/planning-artifacts/epics.md:782` "the new draft stays in the Upgrade Plan and cannot be confirmed until the active attempt is terminal"). A dev implementing UX-PB.1b (sidecar opens on first addition) and UX-PB.3a (sidecar becomes the live summary) has no rule for the overlap. *Fix:* state which object owns the sidecar while an attempt is live, and where the other goes — the realistic options are that new draft additions are refused with an explanation until the attempt is terminal, or that the sidecar gains an explicit two-section/tabbed contract. Pick one and name the focus and announcement behaviour for it.

- **[critical]** **`Verifying` — the state the entire verification-gated trust story depends on — appears zero times in `DESIGN.md` and is missing from both spines' Activity Operation Row state lists.** `grep -ci "verifying" DESIGN.md` returns `0`; `grep -ci "verifying" EXPERIENCE.md` returns `1`, at `EXPERIENCE.md:228`. Quote: "A successful process exit remains `Verifying` until affected Manager state refreshes." That single mention sits under *Results and recovery*, not under the component that must render it. `DESIGN.md:215` lists the Activity Operation Row's required states as "Queued, waiting, running indeterminate, running determinate, stalled, interaction required, cancelling, verified, failed, cancelled, skipped, timed out" — twelve states, none of them `Verifying`. `EXPERIENCE.md:155` lists eleven, also omitting it. Yet Story UX-PB.3c requires it as a live per-item state and names it a durable wire state (`epics.md:805` "AD-16 (`Verifying`/`Skipped` as durable wire states)"; `epics.md:818` "an unverified successful exit remains `Verifying`"). The consequence is that `DESIGN.md:236`'s promise — "Verify refreshed state before coloring an update successful" — has no visual contract at all: no chip, no color token, no row treatment for the window in which verification is pending. *Fix:* add `Verifying` to the Activity Operation Row required states in both spines, assign it a token (it is not `success` and not `warning` — `info` is the only defined fit per `DESIGN.md:131`), and state the row treatment during the verification window.

- **[critical]** **The control that stops a machine-mutating run has two different labels in one document, and the generic label is explicitly reserved for a non-mutating action.** `EXPERIENCE.md:155` (Component Patterns) quote: "Stalled rows expose exactly `Keep waiting`, `Copy command`, and `Cancel`". `EXPERIENCE.md:216` (State Patterns) quote: "the stalled Operation presents exactly `Keep waiting`, `Copy command`, and `Cancel plan`." Both say "exactly", so both claim to be the closed list. The document's own glossary makes the difference load-bearing — `EXPERIENCE.md:110` "Generic `Cancel` is reserved for closing / a dialog or retry-scope editor without mutating running work." A dev building from the component table therefore ships a button labelled `Cancel` — which by this document's own definition means "close this without mutating running work" — wired to plan-wide cancellation that kills every running process group and skips the remainder. That is the worst available mislabel on the one irreversible control. *Fix:* correct `EXPERIENCE.md:155` to `Cancel plan`. `DESIGN.md` contains the string `Cancel plan` zero times (`grep -c "Cancel plan" DESIGN.md` = `0`) — add it to the Activity Operation Row visual contract so the label is pinned in both spines.

- **[high]** **At the guaranteed 900 × 600 minimum with the sidecar open, the authoritative mockup's own CSS pushes status and version evidence off-screen — contradicting `DESIGN.md`'s explicit promise to preserve exactly those.** `DESIGN.md:171` quote: "At the minimum window size and ordinary zoom, preserve the sidebar, the primary action, status words, and version evidence". The arithmetic from `mockups/manager-workspace.html`, which declares `min-width: 900px` on both `html` (line 32) and `body` (line 37) with `box-sizing: border-box` (line 19): `.shell` is `grid-template-columns: 190px minmax(0, 1fr)` (line 138), leaving 710px; `.content-shell` is `grid-template-columns: minmax(0, 1fr) 370px` with `gap: 14px` and `padding: 16px` (lines 300-303), so the grid column gets 710 − 32 − 14 − 370 = **294px**. `.grid-row` declares `min-width: 560px` with columns `44px minmax(150px, 1.4fr) minmax(120px, 1fr) 105px 105px` (lines 522-525) — and per the header row at `manager-workspace.html:1257-1260` those last three columns are `Version`, `Status`, and `Source`. At 294px the Version column already starts past the viewport edge, so all three sit behind the `overflow: auto` horizontal scroll (line 515). The high-zoom rule cannot rescue this because its trigger measures the *window*, not the pane: `DESIGN.md:173` "whenever the usable CSS width drops below 720px", and at a 900px window the usable width is 900. Nothing in either spine keys any behaviour off main-pane width. *Fix:* either add a pane-width trigger (the sidecar collapses to a summary bar, or the grid drops to a stacked two-line row, below a stated main-pane width), or raise the window minimum, or explicitly amend `DESIGN.md:171` to concede that version and status evidence scroll horizontally at the minimum. The current text promises something the layout cannot deliver.

- **[high]** **No plan-level progress summary is specified for a run in flight — the exact case where 3 of 12 are verified, one is running, and one is stalled.** The draft has an exact summary contract (`EXPERIENCE.md:180` "the `Updates`, `Managers`, and `Commands` counts, Manager groups, and button label update immediately") and the terminal state has an exact string (`EXPERIENCE.md:242` "`10 of 12 verified · 2 failed`"), but the in-flight equivalent is only gestured at. `EXPERIENCE.md:424` (AJ-4 step 1) quote: "the sidecar and Activity show the active plan with exact Manager/item counts" — which counts, in what wording, is never said. The one adjacent rule is permissive and Manager-scoped, not plan-scoped: `EXPERIENCE.md:213` "A Manager **may** show exact completed/total item counts even when the current command has indeterminate progress." `DESIGN.md:213` gives the sidecar an `executing` required state with no specified content. This also leaves an accessibility requirement unbuildable: `EXPERIENCE.md:322` requires the status channel announce "each Manager's completion summary" — wording that is never supplied. *Fix:* specify the executing-sidecar summary line and its mixed-state wording, in the same style as the terminal string, and state whether items still queued are counted in the denominator.

- **[high]** **The per-item terminal taxonomy has four values and cannot express two outcomes the Activity model and the epic both require.** `EXPERIENCE.md:227` quote: "Per-item states: verified, failed, cancelled, skipped." First gap: `timed out` is an Operation-level ending — `EXPERIENCE.md:218` "At the 30-minute hard cap, the Operation ends as `Timed out`" — and is a required Activity Operation Row state (`DESIGN.md:215`), but it is absent from the per-item list, so a timed-out item's appearance in Results is undefined. It exists only as an *overall* state at `EXPERIENCE.md:226`. Second gap: Story UX-PB.3d requires a distinction the spines cannot represent — `epics.md:840` "mutation failure and verification failure are distinguished", and `epics.md:844` "then reports verification failure with its evidence". With one `failed` bucket, a dev must invent the distinction or drop it, and dropping it defeats the verification gate. *Fix:* extend the per-item list to cover `timed out` and a distinct verification-failure value, and say which of the six overall states each per-item outcome rolls up into.

- **[medium]** **`Interaction required` is named and given actions, but never specified as resolvable — and its action list conflicts between two lines.** `EXPERIENCE.md:217` quote: "That state includes a plain-language explanation plus `Copy command` and `Cancel plan`; Pack-Manager never accepts the response." No transition out of the state is defined: `Copy command` explicitly does not touch the process (`EXPERIENCE.md:216` "hands control to the user in Terminal and does not alter the running process"), so a user who resolves the prompt in Terminal has no specified way for the row to recover, and the only defined exits are cancelling the whole plan or waiting out the 30-minute cap. Separately, `EXPERIENCE.md:209` offers `Keep waiting` for this state — "when an Operation stalls **or requires trusted-classified interaction** … place `Keep waiting`, `Copy command`, `Cancel plan` … in full Activity" — while `EXPERIENCE.md:217`'s list omits it. *Fix:* reconcile the two action lists, and state explicitly whether `Interaction required` is terminal-by-timeout (which appears to be the intent) or whether resolving the prompt externally can return the row to `running`. If it is effectively unrecoverable, the user-facing explanation should say so, because a user staring at a blocked row will otherwise wait 30 minutes.

- **[medium]** **The point of no return is unspecified: `confirming` is named only in `DESIGN.md`, and `EXPERIENCE.md` never uses the word.** `DESIGN.md:213` gives the Upgrade Sidecar a `confirming` required state and `DESIGN.md:214` gives the Confirmation Dialog one; `grep -n "confirming" EXPERIENCE.md` returns no match. The gap is visible in a guard that describes a state `EXPERIENCE.md` never permits to exist — `EXPERIENCE.md:154` "Escape/backdrop dismiss only when no command has begun", and `EXPERIENCE.md:270` "Backdrop click may close an idle Confirmation Dialog, never a running operation" — both imply a window in which the dialog is open while commands run, yet the focus matrix closes the dialog on confirmation unconditionally (`EXPERIENCE.md:297` "Final confirmation | Close the dialog and move focus to the programmatically focusable Upgrade Activity summary heading"). On the irreversible path the unanswered question is precise: between pressing final confirm and atomic admission returning, is Escape honoured? *Fix:* define `confirming` in `EXPERIENCE.md` — what the dialog and sidecar show, whether dismissal is refused, and where focus sits if admission fails (`EXPERIENCE.md:200` says the dialog "explains why" but not where focus goes).

- **[medium]** **`plan stale` is enumerated as a dialog state with no transition specified anywhere.** `DESIGN.md:214` lists the Confirmation Dialog states as "Open, checkbox off/on, confirming, plan stale, error". `EXPERIENCE.md`'s entire Confirmation section (lines 193-201) never mentions staleness; its only stale rules are `EXPERIENCE.md:191`, which sits under *Draft Upgrade Plan* — "Stale plan: replace invalidated details, explain what changed, and require a fresh confirmation" — and `EXPERIENCE.md:400`, which places the event mid-dialog: "7. If the plan became stale, Pack-Manager replaces the affected preview, explains the change, and requires reconfirmation", between step 6 (dialog opens) and step 8 (final confirmation). So the dialog must handle staleness, but whether it stays open, what happens to the final confirm button, and where focus lands are all undefined. *Fix:* add a stale-in-dialog rule to the Confirmation section and a row to the Focus transitions matrix.

- **[medium]** **The most irreversible button in the product is specified in the color token defined to mean "successfully completed", pre-coloring an outcome the spine insists must be earned.** `DESIGN.md:214` quote: "neutral `Change Plan`, green final confirm". `DESIGN.md:127` defines that token: "`success` | `#72E6A0` | Verified current or successfully completed". This sits against `DESIGN.md:236` "Verify refreshed state before coloring an update successful" and `EXPERIENCE.md:142` "Danger styling is reserved for destructive or cancel consequences" — while the spine's own account of the action is that it is irreversible (`EXPERIENCE.md:216` "states that rollback is not promised"). `EXPERIENCE.md` never names the dialog's final button label or color at all, so `DESIGN.md` is the sole source and it points at the success token. *Fix:* decide deliberately and record it. If green is intended as an affirmative-action convention rather than an outcome claim, say so beside `DESIGN.md:127` so the token's stated purpose and its use stop contradicting; otherwise use the accent primary and reserve `success` for verified outcomes.

- **[low]** **`DESIGN.md` requires two distinct running states; `EXPERIENCE.md` defines one.** `DESIGN.md:215` lists "running indeterminate, running determinate" as separate required states; `EXPERIENCE.md:155` lists only "running". The behaviour is covered — `EXPERIENCE.md:212` "Running progress is indeterminate unless the adapter provides a trustworthy measurable total" — so this is a state-list mismatch rather than a missing decision, but a dev building a state enum from `DESIGN.md` and a renderer from `EXPERIENCE.md` will produce two different sets. *Fix:* make the two lists identical; a single `running` state with a progress-availability flag matches the behavioural rule better than two states.

## Verified-adequate (no action)

- **Plan editability and removal.** Every entry point stages independently removable items, with the Remove control's accessible name specified (`EXPERIENCE.md:147` "accessible name `Remove <Manager> update from Upgrade Plan`"). Fully determined for UX-PB.1c.
- **Bulk-selection scope.** The virtualization trap is closed in three places (`EXPERIENCE.md:143`, `:182`, `:286`) with the exact label form and mixed-state rule. No dev guesswork.
- **"Preserve last-good data after refresh failure and label its age"** is backed by mechanism, not slogan: `EXPERIENCE.md:173` specifies retention, timestamp, `Warning` health, and `Retry refresh`; `:174` forbids the empty-table failure mode; `:120` supplies the copy pattern "Showing snapshot from 10:42 AM".
- **"Do not fabricate progress percentages"** is backed: `EXPERIENCE.md:212` conditions determinate progress on adapter capability rather than UI judgment, and `:308` restates it for the indicator.
- **No-sudo / no-inline-prompt safety.** Consistent across `EXPERIENCE.md:215`, `:217`, `:370`, and `:460`, with the copy-to-Terminal handoff as the specified alternative. Coherent.
- **Retry lineage and History immutability.** One entry per confirmed attempt, `Retry of plan from <time>` linkage, original never rewritten (`EXPERIENCE.md:96`, `:232`, `:238`). Matches D29 and UX-PB.4a/4d without drift.
- **Focus transitions matrix** (`EXPERIENCE.md:292-302`) covers the dialog, the Activity and Results transforms, retry scope, and replay-during-live. Notably complete for a spine at this stage; the only missing rows are the ones named in Findings 8 and 9.
- **Confirmation-off escape hatch.** The persistent warning string, the Settings link, the relabelled action, and the dialog-only location of the opt-out are all specified (`EXPERIENCE.md:154`, `:190`, `:251`, `:258`) and match D28. The safety story here is coherent — the hole this review found is not in the preference, it is in the absence of a cancel control once a run has started (Finding 3).
